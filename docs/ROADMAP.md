# خارطة طريق WICK

الترتيب هنا مقصود: كل مرحلة تبني على اللي قبلها، ولا ننتقل لمرحلة قبل ما تتحقق شروط الإنجاز للمرحلة الحالية. المبدأ الحاكم: **المنصة تحرّك مالاً حقيقياً، فالجودة والأمان قبل الميزات.**

الحالة الآن (سبتمبر 2026): الكود يبني ويتحقق نوعياً ويمرّ 19 اختباراً، البيانات كلها من مصادر حقيقية، ولا توجد بيئة تشغيل حقيقية ولا CI بعد.

---

## المرحلة 0: الحوكمة وبوابات الجودة (أسبوع واحد)

الهدف: ما يدخل شي إلى `main` إلا عبر PR مراجَع وبوابات خضراء.

- [ ] **GitHub Actions**: workflow واحد على كل PR وعلى `main` يشغّل `typecheck` و`lint` و`format:check` و`test` و`build`، ثم `smoke` على الناتج المبني.
- [ ] **حماية الفرع `main`**: منع الدفع المباشر، مراجعة واحدة على الأقل، CI أخضر إلزامي، تاريخ خطي (squash merge).
- [ ] **Conventional Commits** مع فحص آلي (commitlint) وتوليد `CHANGELOG.md` وإصدارات semver عبر tags.
- [ ] **قوالب**: `PULL_REQUEST_TEMPLATE.md` بقائمة فحص (اختبار أُضيف؟ تأثير على التوقيع؟ ADR؟)، قوالب issues للخطأ والميزة، `CODEOWNERS`.
- [ ] **سجل القرارات المعمارية** `docs/adr/`: أول ثلاثة قرارات توثّق ما اتُّخذ فعلاً: لماذا محفظة ساخنة في المتصفح، لماذا DexScreener وpump.fun كمصادر، لماذا `null` بدل التقدير.
- [ ] **التبعيات**: Dependabot أو Renovate أسبوعياً، و`npm audit --audit-level=high` يفشل الـ CI.
- [ ] `SECURITY.md` بقناة إبلاغ عن الثغرات، و`CONTRIBUTING.md` بقواعد الفروع والمراجعة.

شرط الإنجاز: PR تجريبي يفشل لو كسر اختباراً، وينجح لو كان نظيفاً، ولا يمكن دمجه بدون مراجعة.

## المرحلة 1: بيئة تشغيل حقيقية (أسبوع إلى أسبوعين)

الهدف: نشر staging وproduction يعملان على بنية تصمد أمام مستخدم حقيقي.

- [ ] `SOLANA_RPC_URL` على مزوّد مخصص (Helius أو Triton) مع اختبار صحة عند الإقلاع.
- [ ] **محدّد طلبات حقيقي** خارج الذاكرة (Upstash Redis أو ما يعادله) لمسارات `swap` و`send` و`pulse` و`holders`.
- [ ] **cache مشترك** لنتائج pump.fun وDexScreener وتدقيق الـ mint بدل ذاكرة كل instance.
- [ ] بيئتان منفصلتان بمتغيّرات منفصلة، وstaging يشير إلى نفس المصادر لكن بمحفظة اختبار صغيرة.
- [ ] **المراقبة**: Sentry للأخطاء في المتصفح والخادم، logs مهيكلة (JSON) لكل مسار API مع زمن الاستجابة وحالة المصدر الخارجي، ولوحة بسيطة لنسبة فشل pump.fun وDexScreener.
- [ ] مسار `GET /api/health` يعيد حالة كل مصدر.

شرط الإنجاز: staging يعمل 72 ساعة متواصلة بدون تدخل، ولوحة المراقبة تظهر نسب الفشل.

## المرحلة 2: تقوية التنفيذ قبل أي مبلغ يُعتدّ به (أسبوعان)

الهدف: كل معاملة تُوقَّع بعد محاكاة، ولا تُوقَّع مرتين، ونتيجتها تُقرأ من السلسلة لا تُقدَّر.

- [ ] **محاكاة قبل الإرسال** عبر `simulateTransaction`، ورفض أي معاملة تفشل المحاكاة أو يتجاوز أثرها السعري الحد.
- [ ] **انتهاء الصلاحية وإعادة المحاولة**: احترام `lastValidBlockHeight`، إعادة الاقتباس عند الانتهاء، وعدم إعادة إرسال معاملة قد تكون نُفّذت.
- [ ] **idempotency** لكل وظيفة سلسلة: معرّف ثابت للوظيفة، وقفل يمنع التوقيع المزدوج حتى عبر إعادة تحميل الصفحة.
- [ ] **رسوم أولوية ديناميكية** من `getRecentPrioritizationFees` بدل رقم ثابت، وخيار Jito للقنص.
- [ ] **PnL من السلسلة**: قراءة الأرصدة قبل وبعد كل معاملة مؤكدة لحساب التكلفة الفعلية والعائد، وتخزينها مع الـ fill.
- [ ] **حدود صلبة** لا يتجاوزها أي مسار تلقائي: حد لكل معاملة، حد يومي، ومفتاح إيقاف عام (kill switch) يوقف كل التوقيع فوراً.
- [ ] اختبارات تكامل للمسار الكامل اقتباس ← بناء ← توقيع ← إرسال على devnet أو mock لـ Jupiter.

شرط الإنجاز: 50 معاملة متتالية على staging بدون توقيع مزدوج ولا معاملة منتهية الصلاحية.

## المرحلة 3: جودة الكود والبنية (أسبوعان، بالتوازي مع المرحلة 2 حيث أمكن)

الهدف: كود يقدر مطوّر جديد يفهمه ويعدّله بأمان.

- [ ] **تقسيم المتجر** `src/lib/store.ts` (نحو 1300 سطر) إلى شرائح مستقلة: المحفظة، المتابعات والنسخ، الأوامر (snipe/limit/ladder/dca/exits)، الشريط والتنبيهات، الإعدادات. كل شريحة باختباراتها.
- [ ] **طبقة مصادر بيانات موحّدة**: واجهة `Source` واحدة (fetch, ttl, health) تلتزم بها pump.fun وDexScreener والـ RPC، وأخطاء مصنّفة (شبكة، حد طلبات، بيانات ناقصة).
- [ ] **الاختبارات**: هدف تغطية 70% لـ `src/lib`، اختبارات مكوّنات بـ Vitest وTesting Library للتذكرة ولوحة المحفظة، وe2e بـ Playwright لثلاثة مسارات حرجة (إنشاء محفظة، تأكيد الشراء، تفعيل القنص الحي).
- [ ] **تشديد الأدوات**: `no-explicit-any` مفعّل، `exhaustive-deps` خطأ لا تحذير، `noUncheckedIndexedAccess` في tsconfig، وPrettier في CI.
- [ ] **العربية فعلياً**: النصوص موجودة بالكامل لكن الواجهة مقفلة على الإنجليزية؛ تفعيل التبديل مع RTL كامل واختبار بصري لكل صفحة.
- [ ] توثيق داخلي: `docs/ARCHITECTURE.md` بمخطط تدفق البيانات ومسار التوقيع.

شرط الإنجاز: لا ملف يتجاوز 400 سطر في `src/lib`، والتغطية مقاسة في CI ولا تنزل.

## المرحلة 4: عمق البيانات (ثلاثة أسابيع)

الهدف: إشارات أدق بنفس مبدأ الصدق: كل رقم له مصدر.

- [ ] **بث لحظي** عبر WebSocket أو webhooks من Helius بدل الاستطلاع كل 7 ثوانٍ.
- [ ] **شموع تاريخية** من مصدر OHLC حقيقي (Birdeye أو DexScreener) بدل البناء من الاستطلاعات فقط.
- [ ] **كشف الحزم والقنّاصة** بتحليل أول N معاملة على الـ mint (Helius parsed transactions)، وهو ما يعيد حقول `bundled` و`snipers` لكن بمصدر حقيقي هذه المرة.
- [ ] **تتبّع محفظة المطوّر** من حقل `creator` في pump.fun، وتنبيه عند بيعه.
- [ ] عدّاد الحاملين لكل عملة في القائمة (لا في صفحة العملة فقط) عبر RPC المخصص مع cache.

شرط الإنجاز: كل حقل جديد له صف في جدول المصادر في README، وله اختبار يثبت أنه `null` عند غياب المصدر.

## قواعد ثابتة عبر كل المراحل

1. **لا رقم بلا مصدر.** أي حقل جديد إما يأتي من مصدر موثّق أو يظهر `n/a`.
2. **لا توقيع بلا بوابة.** أي مسار جديد يحرّك مالاً يمرّ بحدود الخطر ومفتاح الإيقاف والمحاكاة.
3. **لا دمج بلا CI أخضر ومراجعة.**
4. **لا ملف يكبر بلا اختبار.** التغطية لا تنزل عن القيمة المسجّلة.
5. **قرار معماري = ADR.** ما لم يُكتب لا يُعتبر قراراً.
