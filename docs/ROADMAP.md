# خارطة طريق WICK (نسخة المحرك)

المبدأ الحاكم: المنصة تحرّك مالاً حقيقياً، فالجودة والأمان قبل الميزات. التفاصيل المعمارية في `docs/ENGINE.md`، والقرارات في `docs/adr/`.

الحالة (سبتمبر 2026): مكتب يدوي يعمل ببيانات حقيقية، يبني ويجتاز 20 اختباراً، بلا CI وبلا خادم.

---

## المرحلة 0: الحوكمة وبوابات الجودة (أسبوع)

- [ ] GitHub Actions على كل PR: typecheck، lint، format:check، test، build، smoke.
- [ ] حماية `main`: لا دفع مباشر، مراجعة واحدة، CI أخضر، squash merge.
- [ ] Conventional Commits مع commitlint، CHANGELOG، tags.
- [ ] قوالب PR وissues، CODEOWNERS، SECURITY.md، CONTRIBUTING.md.
- [ ] Dependabot أسبوعياً و`npm audit --audit-level=high` في CI.
- [ ] تحويل المستودع إلى monorepo خفيف: `apps/desk` (الحالي)، `apps/engine`، `packages/core` (المنطق المشترك: risk، exits، entry، guard، jup، hot-wallet).

شرط الإنجاز: PR يفشل لو كسر اختباراً ولا يُدمج بلا مراجعة.

## المرحلة 1: الخادم والبيانات (أسبوعان)

- [ ] VPS بـ Docker Compose: engine، Postgres+Timescale، Redis، Prometheus، Grafana، نسخ احتياطي يومي.
- [ ] مخطط قاعدة البيانات من ENGINE.md §6 مع migrations.
- [ ] `ingest`: pump.fun وDexScreener وتدقيق mint (نقل الكود الحالي)، إضافة فحص Token-2022 (الامتدادات) وحالة LP الثلاثية.
- [ ] Helius webhooks لأحداث الإنشاء والهجرة وصفقات المحافظ المتابَعة (بدل الاستطلاع).
- [ ] `features` كل ثانية لكل mint نشط، مع `uniqueBuyers5m` من الأحداث.
- [ ] `/metrics` والمقاييس الأربعة عشر، لوحتا Operations وQuality.
- [ ] RPC مخصص مع مزوّد ثانٍ احتياطياً، وفحص صحة على حداثة الـ slot لا على HTTP 200.

شرط الإنجاز: 72 ساعة بث بلا انقطاع، ولوحة Operations تُظهر عمر كل مصدر.

## المرحلة 2: القرار والبوابات والتنفيذ في وضع الاقتراح (ثلاثة أسابيع)

- [ ] `decision` بقاعدتي `confirmed-entry` و`exit-policy` وأوزان من `rules.yaml`.
- [ ] البوابات الست بأكواد الرفض من ENGINE.md §3، كل رفض يُكتب.
- [ ] `executor`: محاكاة، توقيع بالمفتاح المختوم، إرسال، تأكيد، قراءة الأرصدة قبل وبعد، idempotency بقفل لكل نية.
- [ ] الخزنة على الخادم وفتحها من لوحة التحكم، مفتاح الإيقاف كملف، سقوف المحفظة في الكود.
- [ ] لوحة التحكم (التطبيق الحالي): قائمة النوايا مع سبب كل قرار، موافقة/رفض، Telegram بأمر موقّع للإيقاف.
- [ ] `outcomes` لكل نية بعد 5 و30 و120 دقيقة، منفَّذة أو مرفوضة.
- [ ] اختبارات تكامل للمسار الكامل على devnet.

شرط الإنجاز: 30 يوماً في وضع suggest بمحفظة 3 SOL، 50 نية منفَّذة بلا توقيع مزدوج ولا معاملة منتهية، وتوزيع أكواد الرفض يُقرأ من اللوحة.

## المرحلة 3: التعلّم المستوى 2 والوضع التلقائي (ثلاثة أسابيع)

- [ ] `evaluator` اليومي: إحصاءات القواعد على 14 يوماً، أوزان محدودة الحركة، تعطيل القاعدة السالبة، كل تغيير بسبب مسجّل.
- [ ] تقييم المحافظ المتابَعة بفجوة النسخ والانزلاق، وخفض الرتبة.
- [ ] الترقية إلى auto لكل قاعدة بشروط ADR-0004، والعودة التلقائية إلى suggest.
- [ ] `migration-snipe` عبر webhook في وضع suggest.
- [ ] تقرير يومي على Telegram: الأداء، أكثر أكواد الرفض، ما تغيّر في الأوزان ولماذا.

شرط الإنجاز: قاعدة واحدة على الأقل استحقت auto بشروطها، وشهر كامل بلا حادثة تشغيلية.

## المرحلة 4: عمق الكشف (أربعة أسابيع)

- [ ] تحليل شجرة التمويل لأكبر الحاملين (`MANIP_FUNDING`) كوظيفة خلفية لا في المسار الساخن.
- [ ] كشف الحزم من معاملات الإطلاق الأولى.
- [ ] كشف الغسل بالرسم الدائري وانتظام التوقيت.
- [ ] شموع تاريخية من مصدر OHLC.

## المرحلة 5: الصلابة والأمان (أسبوعان)

- [ ] نموذج تهديد مكتوب ومراجعة أمنية خارجية.
- [ ] CSP صارم وخطوط محلية في لوحة التحكم، مصادقة بمفتاح عتادي أو passkey.
- [ ] تمارين فشل: قطع RPC، توقف Postgres، إعادة تشغيل غير مراقبة؛ كل واحد لازم ينتهي بتوقف آمن.
- [ ] مراجعة قرار الحفظ (ADR-0003) بحسب حجم رأس المال.

## المرحلة 6: التعلّم المستوى 3 (بعد 2,000 نية مسجّلة)

- [ ] نموذج تنبؤي يُدرَّب على `intents` و`outcomes`، يُختبر بالورق 30 يوماً، ويقتصر أثره على تعديل الحجم داخل حدود البوابات.

## قواعد ثابتة عبر كل المراحل

1. لا رقم بلا مصدر؛ المجهول `null` ويظهر n/a ويرفضه الفلتر.
2. لا توقيع بلا بوابات كاملة؛ الموافقة البشرية لا تتجاوز بوابة.
3. المال يتوقف في المحرك لا في التنبيه.
4. لا دمج بلا CI أخضر ومراجعة، ولا ملف يكبر بلا اختبار.
5. كل تعديل ذاتي للمحرك له صف مسجّل بسبب ورقم.
6. قرار معماري = ADR.
